# FlyBrain-Controlled Robot Project — Code File Summary

## 1. Project Overview

My project involves using an open-source fruit fly brain simulation (FlyBrain) to control a physical robot. The goal is to explore whether neural activity from the simulated fly brain can be used to make movement decisions based on sensor inputs.

I am using an ESP32 microcontroller to read physical sensors and control the motors, while my laptop runs Python and the FlyBrain simulation. The laptop and ESP32 communicate through a USB serial connection.

My planned hardware inputs include an ultrasonic distance sensor and two infrared (IR) obstacle sensors. The ultrasonic sensor measures the distance to an obstacle, while the IR sensors provide additional information about obstacles on the left and right sides.

The overall system is intended to work as follows:

1. The ESP32 reads the ultrasonic and IR sensors.
2. The ESP32 sends the sensor readings to my laptop through USB serial.
3. A Python program receives the readings and converts them into inputs for the FlyBrain simulation.
4. The simulation produces neural activity that I can use to help determine the robot's movement.
5. Python sends a movement command back to the ESP32.
6. The ESP32 controls the motor driver to move or stop the robot.

This is an experimental mapping between physical sensors and a simulated biological neural network. The mapping is an engineering approximation rather than a biologically validated representation of how a fly processes these sensors.

## 3. Planned Main Program Files

### esp32.ino

This will be the main Arduino C++ firmware running on the ESP32.

Its responsibilities will include:
- Reading the ultrasonic distance sensor.
- Reading the left and right IR sensors.
- Sending sensor readings to the laptop through USB serial.
- Receiving movement commands from Python.
- Controlling the motors through the motor driver.
- Stopping the motors when a safety condition is triggered or communication is lost.

The ESP32 will handle the physical hardware, while the laptop will handle the FlyBrain simulation and decision-making.

### fly.py

This will be the main Python controller running on my laptop.

Its responsibilities will include:
- Establishing serial communication with the ESP32.
- Receiving and interpreting sensor readings.
- Converting sensor information into an appropriate input for the FlyBrain simulation.
- Running or updating the simulation.
- Inspecting relevant neural activity.
- Mapping the neural output to movement commands.
- Sending movement commands back to the ESP32.

The exact FlyBrain API calls still need to be verified against the installed package and the experiments in my notebook. The final implementation will depend on how the simulation accepts external inputs and exposes neural activity.

## 4. Testing Files

### sensor_interpretation_test.py

This is a software-only Python test that checks how sensor readings are interpreted.

It can simulate different sensor conditions without requiring the physical robot. For example, I can test whether an obstacle detected at a short distance causes the program to select a stop command.

The current starter version uses simple rule-based logic to produce commands such as:
- F: Move forward.
- L: Turn left.
- R: Turn right.
- S: Stop.

This test helps me check the basic decision-making logic before integrating the FlyBrain simulation. It does not test physical sensors or FlyBrain itself.

### laptop_to_esp.py

This Python file tests serial communication between my laptop and the ESP32.

It is intended to help me:
- Identify available serial ports.
- Read messages sent by the ESP32.
- Send simple movement commands to the ESP32.
- Check whether the laptop and microcontroller can exchange data.

This test requires the ESP32 to be connected and running compatible firmware. It does not independently test the physical sensors, FlyBrain, or the motors.

### esp_test.ino

This is a simple ESP32 sketch for testing how incoming serial commands are received and interpreted.

It accepts commands such as F, L, R, and S and reports whether the command is valid. The starter version does not move the motors.

This lets me test the command format and serial communication before allowing commands to control physical hardware.

### sensor_test.ino

This will be an Arduino C++ test sketch for the physical sensors.

It will read the ultrasonic distance sensor and the left and right IR sensors, then print their readings to the Serial Monitor.

This test helps me verify:
- Whether the sensors are connected correctly.
- Whether the ESP32 reads the expected pins.
- Whether the ultrasonic sensor reports plausible distances.
- Whether the IR sensors change state when obstacles are detected.

Unlike test_sensor_logic.py, this test requires the physical sensors and ESP32.

### motor_test.ino

This will be an Arduino C++ test sketch for checking the motors and motor driver independently of FlyBrain.

It will allow me to test whether each motor responds correctly to basic movement commands. I can use it to identify wiring problems, incorrect motor directions, or motor-driver issues before integrating the full system.

The wheels should be lifted off the ground during initial testing. The motor supply, driver wiring, and common ground must be checked before powering the motors.

## 5. Testing and Integration Sequence

I plan to develop and test the project in stages so that I can identify problems without debugging the entire system at once.

Step 1: Explore the FlyBrain simulation.
Use quickstart.ipynb, test_neurons.py, and test_escape.py to understand the neural network and investigate potential movement-related neuron populations.

Step 2: Test the basic sensor logic.
Run test_sensor_logic.py on my laptop with simulated sensor values. Confirm that expected conditions produce the appropriate commands.

Step 3: Test the ESP32 command parser.
Upload test_command_parser.ino and verify that the ESP32 correctly receives commands over serial without moving the motors.

Step 4: Test the physical sensors.
Upload test_sensors.ino once the ESP32 and sensors are available. Verify the readings before integrating them with Python.

Step 5: Test the motors.
Use test_motors.ino to check the motor driver, motor directions, and basic movement commands. Test with the wheels lifted and keep the motor power disconnected while checking wiring.

Step 6: Test serial communication.
Use test_serial.py with compatible ESP32 firmware to verify that sensor messages can reach the laptop and commands can be sent back.

Step 7: Integrate the FlyBrain simulation.
Develop flybrain_robot.py to convert sensor information into simulation inputs, inspect neural responses, and map those responses to movement commands. Verify the input and output interfaces against the installed FlyBrain package.

Step 8: Integrate the complete robot.
Combine the sensor, serial, FlyBrain, and motor-control components. Test each part separately before allowing the full system to control the robot.

Step 9: Evaluate and improve the system.
Record sensor values, neural activity, and movement decisions. Compare the FlyBrain-controlled approach with a simple rule-based baseline to determine whether the neural simulation improves the robot's responses.

## 6. Important Implementation Notes

- The laptop runs Python and FlyBrain; the ESP32 runs Arduino C++.
- USB serial is the communication link between the two.
- The ESP32 GPIO pins are not 5 V tolerant. If my ultrasonic sensor uses a 5 V Echo output, I need an appropriate voltage divider or level shifter.
- The motor driver needs an appropriate motor supply, and the ESP32 and motor-driver circuit need a common ground.
- I need to check the exact wiring and whether the motor driver board requires its nSLEEP pin to be enabled.
- The robot should have a reliable stop condition that does not depend entirely on FlyBrain's output.
- The FlyBrain integration code is still a work in progress until I verify the installed package's actual input and output interfaces.
- The physical sensor and motor tests cannot be completed until the relevant hardware is available, but the software-only logic test and FlyBrain notebook experiments can be developed in advance.

## 7. Overall Goal

My goal is to build a working prototype that connects a simulated biological neural network to a physical robot. By developing and testing each component separately, I can investigate how sensor inputs influence neural activity and whether that activity can be used to guide the robot's movement.
